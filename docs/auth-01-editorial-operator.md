# AUTH-01 — Acceso privado de operadores editoriales

## Resultado

AUTH-01 implementa la base de autenticación del espacio editorial con Supabase Auth por código numérico enviado por email. La sesión usa cookies HttpOnly; cada solicitud protegida pregunta al proveedor por la identidad verificada y comprueba su email contra una lista privada. La UI de UI-06 permanece como fixture de desarrollo y ahora también exige un operador autorizado.

El resultado inicial de inventario fue `NO_AUTH_IMPLEMENTATION`: había SDKs de Supabase para contenido público y tareas de servidor, pero no clientes web de Auth, sesión, login, callback o guardas de rutas. El RPC de M32 no constituye autenticación de operador. La inspección de solo lectura de la configuración Auth del proyecto remoto confirmó que el proveedor de email está habilitado, el auto-confirmado desactivado y la creación general de usuarios todavía habilitada. No se escribieron usuarios ni configuración en el proyecto remoto. El transporte SMTP y la entrega a una bandeja real no se pudieron confirmar.

## Decisiones y límites

- Se usa `@supabase/ssr` 0.12.7 con `@supabase/supabase-js` y Next.js 16.3.8. La autenticación utiliza el OTP soportado por Supabase, sin contraseñas propias ni SDK de Auth en el navegador. El flujo pide `shouldCreateUser: false`; una identidad se autoriza únicamente después de verificar `getUser()`, `email_confirmed_at` y la lista explícita de operadores.
- `EDITORIAL_OPERATOR_EMAILS` es una variable privada, separada por comas, punto y coma o líneas. Los emails se normalizan a minúsculas. Una configuración vacía o mal formada cierra el acceso. Nunca se envía la lista al cliente.
- `EDITORIAL_AUTH_URL` y `EDITORIAL_AUTH_PUBLISHABLE_KEY` son opciones privadas de configuración; en su ausencia se usan la URL y la publishable/anon key existentes. No hay fallback a `SUPABASE_SECRET_KEY`. `EDITORIAL_AUTH_ORIGIN` debe ser el origen HTTPS del sitio en producción. Estas variables se documentan en `.env.example`; sus valores reales permanecen locales.
- Las cookies de sesión son HttpOnly, SameSite=Lax, host-only y de siete días; usan Secure en producción. `@supabase/ssr` gestiona renovación y cookies fragmentadas. La autorización llama a `auth.getUser()` y no confía en `getSession()` ni en datos del JWT guardados por el navegador. El cierre solicita revocación local al proveedor y siempre elimina las cookies del dispositivo.
- El proxy protege `/editorial/:path*` y `/api/editorial/:path*` antes de HTML, RSC o respuesta API. Los endpoints de login están excluidos deliberadamente. Las rutas HTML/RSC redirigen con estado genérico; las APIs reservan 401 para sesión ausente/expirada, 403 para identidad no permitida y 503 cuando falta configuración o Auth no está disponible. No hay URL de retorno libre.
- `requireEditorialOperator()` es la guarda canónica para componentes de servidor y futuros handlers. La capa de datos de fixtures vuelve a exigirla antes de importar fixtures. La pantalla de login tiene formularios HTML de email/código, no signup, mensajes en español y un botón de cierre para cuentas rechazadas.
- Los POST de Auth aceptan únicamente `Origin` coincidente con el origen configurado y formularios acotados. El proxy y las respuestas privadas usan `no-store`, `noindex` y `Referrer-Policy: same-origin`. Para decisiones futuras, cada ruta deberá exigir sesión y operador, comprobar mismo origen/CSRF, releer el estado actual en servidor y enlazar la revisión, hash y linaje esperados dentro de una operación atómica. AUTH-01 no implementa APPROVE, HOLD ni REJECT.
- El futuro camino M32 es: página/handler de servidor protegido → llamada server-only al RPC de solo lectura con credencial privilegiada → validación de artefactos y pruebas → proyección mínima `EditorialReviewDTO` → render al operador. El navegador nunca llamará RPC privilegiado ni recibirá la service key.
- No se activó M32 ni se añadieron migraciones. Tampoco hubo mutaciones editoriales, publicación, notificaciones push, llamadas de pipeline, cambios de scheduler o despliegue.

## Verificación

El modo local aislado usó Supabase Auth y Mailpit en puertos locales, sin ejecutar las migraciones del repositorio ni contactar el proyecto alojado. Se sembraron dos identidades sintéticas locales. Se probó el envío y verificación OTP, el acceso permitido a los fixtures solo con el operador, la denegación de sesión anónima, expirada, manipulada y de una identidad autenticada ajena a la lista, los endpoints API, el refresco real del SDK, el cierre de sesión y la protección CSRF. Home, mapa, noticia pública y páginas legales siguieron disponibles sin sesión. Evidencia sanitizada: `artifacts/auth-01/local-integration.json`.

Las pruebas deterministas de política/resolución (8 grupos) y la regresión UI-06 (11 grupos) pasaron. La compilación de producción pasó con Next.js 16.3.8 y completó TypeScript; para la descarga de Google Fonts fue necesario ejecutar la compilación con acceso de red, ya que el primer intento aislado falló en DNS. La actualización de Next parchea el aviso crítico y los avisos de runtime identificados en Next.js 16.3.4. `npm audit` todavía informa ocho avisos altos en dependencias transitivas del árbol de desarrollo/build (`eslint-config-next` y sus patrones, `sharp`, `source-map-js` y `brace-expansion`); el arreglo automático propuesto por el registro para la rama de ESLint implica un salto mayor, por lo que no se aplicó sin una evaluación separada. Revisar actualización compatible en una fase propia.

El QA visual preparado cubre login, errores de expiración y rechazo en 390×844, 430×932, 768×1024 y 1440×900, tanto en modo oscuro como claro cuando aplica. Se comprobó navegación por teclado y controles de OTP. Las capturas están en `artifacts/auth-01/evidence/`. Las dimensiones simulan viewports de navegador; no equivalen a una validación con dispositivo iPhone físico o lector de pantalla. La flag `Referrer-Policy: same-origin` conserva el encabezado Origin requerido por formularios nativos; en pruebas iniciales `no-referrer` lo eliminaba y el servidor rechazaba correctamente la solicitud.

La actualización de `eslint.config.mjs` excluye el directorio local aislado de Auth de ESLint porque contiene archivos efímeros de ejecución y credenciales sintéticas. `git diff --check` terminó con código cero; Git mostró avisos de conversión LF/CRLF en archivos preexistentes.

## Activación y preparación

En producción hay que configurar `EDITORIAL_OPERATOR_EMAILS` y `EDITORIAL_AUTH_ORIGIN` en el runtime privado, confirmar la publishable key del proyecto y verificar la entrega de email de Auth con un buzón autorizado. La configuración remota observada todavía permite signup general; el código de la aplicación no permite que el formulario cree usuarios, pero antes del uso real conviene deshabilitar signup en el proyecto y revisar sus límites de envío/plantilla de email. No se ha enviado ningún email real ni se ha cambiado esa configuración remota.

El proyecto remoto no necesita una tabla o migración para esta guarda. AUTH-01 no quedó listo para datos editoriales en vivo: UI-07 deberá conectar el RPC de M32 solo después de validar el destino y el operador con la configuración de producción; entonces debe probarse otra vez la autorización, la forma del DTO, RLS/ACL y ausencia de filtraciones en HTML, RSC y bundles. Las vistas de fixture existen solo en desarrollo y también están protegidas por Auth.

Para repetir la prueba local, iniciar el stack bajo `.auth-01-local/` con signup global desactivado, proveedor email local habilitado, confirmación requerida y SMTP dirigido únicamente a Mailpit; crear identidades `@example.test` con la API administrativa local, no con la pantalla pública. El archivo de entorno y las cookies de esta prueba se ignoran por Git y deben eliminarse al apagar el stack.
